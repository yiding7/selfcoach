## 它和别的健身工具有什么不同

**换模型不换结果。** 所有分析、指标、图表都由确定性 Python 脚本产出。
模型只负责把结论讲得好听，不负责算数。今天用 Claude、明天用 GPT、后天用本地
Ollama，报表里的吨位、估算 1RM、对比结论**完全一致**。

这不是实现细节，是设计目的：健康记录的价值在于纵向可比。如果数字是模型算的，
换个模型历史就没法对照了。

**对比做得比健身 App 细。** 见 [对比是怎么做的](#对比是怎么做的)。
简单说：普通 App 只会拿这次和上次比，动作换了就废了；
这里用四个视角，每个都带置信度，**比不了的时候明说比不了**，不硬凑结论。

**零依赖。** 只用 Python 标准库。不需要 `pip install`，clone 下来就能跑。

**零外链。** 生成的 HTML 把图表以内联 SVG 写死在文件里。断网能看，
存档十年后还能看，Cmd+P 直接存 PDF，深浅色自动跟随系统。

**有没有训记都能用。**

## 快速开始

```bash
git clone git@github.com:yiding7/selfcoach.git
cd selfcoach
./install.sh              # 建目录、把 skills 链到 agent 宿主。不下载任何东西
cp .env.example .env      # 有训记就填 key；没有就跳过
./scripts/hc doctor       # 体检：环境、凭证、本地数据、个人档案
./scripts/hc sync --since 30d    # 同步（训练接口 30s/天限频，会预告耗时）
```

填一份个人档案，助手的建议会贴合得多：

```bash
cp profile/personal-context.example.md profile/personal-context.md
# 用编辑器填写：病史、用药、伤病、器材、忌口、作息、沟通偏好
```

体检报告直接丢进 `profile/medical/`，文件名带上日期（比如 `2026-04-体检.pdf`），
助手会读取并和历史报告逐项对比。

`profile/` 整个目录不进版本库，放心写。

装上后台自动同步，之后数据自己保持新鲜、对话时不用等：

```bash
hc autosync install
```

## 怎么和助手对话

装好之后，在 Claude Code / Codex / Cursor 里**直接说人话就行**，
助手会自己去跑命令、读数据。下面是常见场景。

### 刚练完，想知道练得怎么样

> 今天练完背了，帮我看看

助手会跑 `hc compare`，然后告诉你：
每个动作和它自己上次比怎么样、发力模式的量变了多少、
过去 28 天的结构有没有失衡、下次该怎么调。

如果这次的动作和上次完全不一样，它会**明确告诉你哪些能比、哪些不能比**，
而不是硬给一个「你退步了」的结论。

### 想知道下次怎么练

> 下次练背该上多少重量

```
hc next 背
```

会给到具体动作、组数、重量、目标次数，以及**为什么**这么建议。
如果你正在明显的减重期，它会说「这个阶段力量维持住就是成功，不追加重量」，
而不是机械地让你每次加 2.5 kg。

### 想看阶段总结

> 出个这周的报告

生成一个自包含 HTML，浏览器打开，Cmd+P 存 PDF。
里面有图表、肌群热力图、逐动作纵向表、结构平衡分析、下次训练建议。

### 补记一次训练

> 今天练胸，卧推 60 公斤做了 10/10/8，上斜哑铃 22.5 三组 12 个

助手会转成速记给你确认，确认后落库。**不用你自己写格式。**

### 问吃的

> 这个能吃吗 / 我蛋白够不够 / 外面吃火锅怎么办

助手会读你的 `profile/food-traffic-light.md` 和个人档案，
结合你自己填写的体检背景与健康约束给判断。

**它不会要求你记录每餐热量** —— 走的是「原则 + 快速判断」路线。

### 问身体数据

> 我最近体重怎么样 / 是不是平台期了

永远用 7 日移动均线说话。日间波动可以到 ±1.8 kg，
看单日读数会得出完全错误的结论。

### 数据不全的时候

> 最近的训练没显示

```
hc sync --since 14d
```

助手会告诉你预计耗时。抓过的日期永不重抓，第二次跑是瞬间完成的。

## 对比是怎么做的

这是整个工具最花心思的部分，也是 AI 分析真正比健身 App 强的地方。

### 问题

每次训练的选材都在变。同样是练背：

- 第一次：多做划船，少做高位下拉
- 第二次：多做高位下拉，没做划船，但做了引体
- 第三次：宽距、窄距、反手三种高位下拉

普通 App 拿「这次 vs 上次」硬比，动作对不上就废了。更糟的是有些工具会硬比峰值重量
——器械推胸 40 kg 和俯卧撑折算的 51 kg 放一起比，得出「力量下降 20%」，
既错误又打击人。

### 解法：四个视角，各带置信度

| 视角 | 回答什么 | 不受什么影响 |
|---|---|---|
| **逐动作纵向** | 这个动作和**它自己**上次比怎么样 | 完全不受选材变化影响 ← 最可靠 |
| **发力模式** | 垂直拉/水平拉这类模式的量变了多少 | 变体互换（宽距↔窄距↔反握）|
| **肌群窗口** | 最近 28 天 vs 前 28 天 | 单次波动 |
| **结构平衡** | 这个部位内部比例合理吗 | —— |

**逐动作纵向**是关键改进：它在**全部历史**里找这个动作上一次出现，
而不是只在「上一次同部位训练」里找。所以宽距高位下拉哪怕隔了三次训练才再做，
也能干净地比出进步。

### 置信度门控

| 置信度 | 含义 | 能比什么 |
|---|---|---|
| `exact` | 同一个动作名 | 重量、次数、1RM 都能直接比 |
| `variant` | 同族不同握法/版本 | 重量大致可比，会标注握法变了 |
| `pattern` | 同模式不同动作 | 只比组数和容量，**不比重量** |
| `group` | 只是同一个部位 | 只比组数和频率 |
| `none` | 数据不足 | 什么都不比 |

**低于门槛就明说「暂时不可比」，等到能比的时候再给结论。**
这是刻意的设计取舍：宁可少说一条，也不要说一条错的。

### 结构平衡 —— 最有价值的一层

看**过去 28 天**每个部位内部各模式的比例。比如实际跑出来的：

```
过去 28 天：水平拉 56 组，垂直拉 21 组，比例 2.7:1
垂直拉练背阔宽度，水平拉练背部厚度和中下斜方。
只练一边会让体态往圆肩方向走，肩胛稳定性也跟不上。
→ 下次背日加一个垂直拉（高位下拉或引体向上）
```

总组数完全达标，但结构是歪的 —— 这种问题普通 App 看不出来。

目前内置的规则：背的垂直/水平拉比例、胸的上斜推占比、肩有没有练后束、
腿的膝主导/髋铰链比例、三头有没有过头伸展。规则在
`knowledge/pattern-balance.json`，可以自己改。

**只看滚动窗口，不看单次。** 单次训练有侧重完全正常，甚至是好事；
值得提示的是持续几周的结构性缺失。

## 报表

```bash
hc report weekly | monthly | yearly
```

产出两个文件：

- `2026-W31.html` —— 完整可读的自包含报告
- `2026-W31.facts.json` —— 算好的事实，给模型写叙述用

**没有模型时报告依然完整**（数据、图表、对比、处方全在，只是少了教练的话）。
有模型时让它读 facts.json 写叙述，再 `hc inject` 注入。

包含：KPI、部位组数堆叠柱、各部位训练量 vs 个体化参考区间、
人体肌群热力图（正反面）、逐动作纵向表、发力模式对比、结构平衡分析、
体重 7 日均线 + 每日散点、训练日历热力图、下次训练建议、数据质量说明。

年报按月聚合（150 次训练逐次画柱子会挤成一团）。

## 没有训记怎么办

这是**一等公民路径**，不是降级方案。

对助手说：
> 今天练胸。卧推 60kg 做了 10/10/8，上斜哑铃 22.5kg 三组 12 个

助手转成速记给你确认，确认后落库。之后的所有分析和训记同步来的数据**完全一样**。

速记语法（也可以直接手写）：

| 写法 | 含义 |
|---|---|
| `60x10` | 60kg 做 10 次 |
| `22.5x12x3` | 22.5kg 做 12 次，共 3 组 |
| `~40x10` | 热身组，不计入有效容量 |
| `62.5x8@8` | RPE 8 |
| `BWx12` / `BW+10x8` | 自重 / 自重加 10kg |
| `T:60s x3` | 计时 60 秒，3 组 |
| `L:20x10 R:22.5x10` | 单侧，分别记左右 |
| `> 睡眠不足` | 整次训练的备注 |

## 数据同步：装一次，之后不用管

**问题**：训记训练接口一天只能查一天，限频 30 秒。如果每次打开助手都要现场同步，
一等十几分钟，这工具就没法用了 —— 助手应该随叫随到。

**解法**：同步挪到后台定时跑，对话时数据本来就是新的。

```bash
hc autosync install        # 装一次就好（macOS 用 launchd，Linux 打印 cron 配置）
```

装完之后：

- 每 3 小时后台跑一次，同步最近 7 天 + 身体数据，再顺带回填 10 分钟历史
- 回填完早期数据后，这一步自然就没活干了
- 日志在 `data/autosync.log`，`hc autosync log` 查看
- 策略写在 `scripts/autosync.sh`，改这个文件即可调整，**不用重装定时任务**
- 卸载：`hc autosync uninstall`

**对话开始时先看新鲜度**，这一步不联网、毫秒返回：

```bash
hc status
```

```
训练数据已抓取 2026-03-01 ~ 2026-08-04（157 天 / 61 次训练）
✅ 最近的日期都已同步，可以直接分析
✅ 体重数据最新到 2026-08-03（1 天前）
✅ 后台自动同步已启用，上次运行 2026-08-04T14:02:11
```

助手被明确要求：看到「都已同步」就直接分析，一个网络请求都不发；
缺很多天时不许默默同步，要先说要等多久、让你决定。

### 为什么稳态下很快

抓过的日期**永不重抓**（空日期也记录），所以稳定运行后每次只有 0~2 个新日期，
几十秒就结束。慢的只有第一次回填：

| 首次回填范围 | 耗时 |
|---|---|
| 30 天 | ≈ 15 分钟 |
| 90 天 | ≈ 45 分钟 |
| 1 年 | ≈ 3 小时 |

其它设计：

- **原始响应原样落盘**。改了解析逻辑跑 `hc rebuild` 离线重算，一次网络请求都不用
- **随时 Ctrl-C 安全**，进度已保存
- 手动分批补历史：`hc sync train --since 2026-03-01 --budget-minutes 20`
- 限频器**跨进程**，后台任务和你手动跑的同步不会互相撞限频

本地缓存很贵，换设备时把 `data/` 带走，别重新拉。

## 苹果健康与有氧

### 导入苹果健康

训记只同步一部分数据。体重、饮酒、睡眠、静息心率、步数这些在苹果健康里，
可以导进来一起分析：

```
iPhone 健康 App → 右上角头像 → 拉到最下面「导出所有健康数据」→ 得到「导出.zip」
```

```bash
hc import-health ~/Downloads/导出.zip --dry-run   # 先看解析出什么
hc import-health ~/Downloads/导出.zip
```

导入：体重（取**当天最早**那条，即晨起空腹值）、体脂、腰围、静息心率、HRV、
步数、饮酒杯数、饮水、睡眠时长（自动排除清醒段，跨夜归到起床那天）。

体重/体脂/腰围会合并进身体数据主存储，报告和趋势分析自动用上。

导出文件常有几百 MB，解析器用流式解析，内存占用是常数级。

### 有氧与心率区间

```bash
hc cardio --window 7
```

用 Tanaka 公式（`208 − 0.7×年龄`，比 `220−年龄` 对成年人更准）算最大心率，
把每次有氧归到 Z1–Z5，并给出周维度的量和强度配比建议。

年龄从 `data/profile.json` 的 `birth_year` 读；做过实测最大心率的话填
`hr_max_override`，实测永远优先于公式。

## 命令一览

```bash
hc status                      # 数据新鲜度（不联网，秒回）
hc doctor                      # 环境体检
hc autosync install|uninstall|log   # 后台自动同步
hc sync [train|body|food]      # 从训记同步
  --since 30d / --until DATE   # 时间范围
  --budget-minutes 20          # 限时分批，适合 cron 补历史
  --force                      # 忽略缓存强制重抓
hc rebuild                     # 用原始缓存离线重算，零网络
hc log                         # 手记训练（--dry-run 先看解析结果）
hc sessions --since 30d        # 列出本地训练
hc summary --date 2026-07-30   # 单次训练详细指标
hc compare [--date] [--group]  # 四视角对比
hc next 背                      # 下次训练建议
hc report weekly|monthly|yearly [--open]
hc inject <报告名> --slot opening
hc classify [--unknown-only]   # 查看/教会动作的肌群归属
  --learn '动作名=部位'
hc cardio [--window 7]         # 有氧与心率区间分析
hc import-health <导出.zip>     # 导入苹果健康
```

## 目录结构与隐私

```
profile/medical/ 体检报告原件（PDF / 图片），**不进版本库**
                 文件名带日期，比如 2026-04-体检.pdf；助手会读取并跨次对比
knowledge/       通用知识，**提交进版本库、可分享**
                 人格、安全边界、动作肌群表、动作模式表、结构平衡规则、训练量参考
profile/         个人隐私，**不进版本库**
                 病史、用药、体检数值、忌口、作息、个人化红黄绿灯
data/            私人数据，**不进版本库**
                 训练记录、体重、饮食、原始缓存
chat-history/    历史对话归档，**不进版本库**
reports/         生成的报告，**不进版本库**
skills/          七个 SKILL.md，交付主体，入口是 health-coach
src/             纯标准库实现
```

`knowledge/` 和 `profile/` 的分界线决定了这个仓库能不能安全地公开分享：
**通用的进 git，只属于你一个人的不进。**

其它隐私措施：

- 四把训记 API key 只存在 `.env`（gitignore）。任何脚本、日志、报告都不会打印
- 接 LLM 适配器做无人值守报告时，**只发送聚合后的 findings**，
  原始餐食、用药、体检数值不出本机
- 想跨设备同步私人数据：在 `data/` 里单独 init 一个私有仓库

## 常见问题

**问：为什么不给我算每餐热量？**
因为工具的定位是「原则 + 快速判断」，不是记账。如果你想精确记录，
训记的饮食接口已经接好了，`hc sync food` 能同步。

**问：估算 1RM 准吗？**
是 Epley 公式推算，不是实测，超过 12 次会标低置信度。
它的价值在于**纵向比较同一个动作**，不适合拿来和别人比、也不适合当作真的极限重量。

**问：为什么有些对比它说「不可比」？**
见 [置信度门控](#置信度门控)。这是刻意的 —— 硬比会得出错误且打击人的结论。
两次训练里保留 1~2 个相同的主项动作，就能一直有可靠的对比。

**问：参考区间（MEV/MAV/MRV）是必须达标的吗？**
不是。那是人群统计值，不是处方，减脂期的可恢复上限还更低。
只用来提示「可能偏少/偏多」，你自己的感受优先。

**问：动作没被正确分类怎么办？**
```bash
hc classify --unknown-only        # 看看有哪些没认出来
hc classify --learn '动作名=背'    # 教一次，以后都认得
```

**问：改了解析逻辑要重新同步吗？**
不用。`hc rebuild` 从本地原始缓存离线重算，零网络请求。
